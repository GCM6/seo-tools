# Veris 产品功能与闭环现状分析（2026-10-08）

> 起因：用户反馈「功能比较混乱，流程不够清晰，并且不够闭环」。
> 方法：只读分析。本地库查询（`veris.db`）+ 浏览器走查主流程（`next start -p 3005`，HEAD `786c18b`）+ 两个只读代理分别梳理页面导航图与状态机，代理的关键论断由主循环抽查复核。
> 标签：**observed** = 本轮亲自读代码、查库或在浏览器看到；**reported** = 代理读代码得出、主循环未逐条复核；**derived** = 由观测推出。

## 〇、结论（先看这段）

10-07 改版的原则是「不删功能，只重组呈现」，所以界面整齐了，下面三个结构问题都没动：

1. **一个导航里放了三个产品**：网站诊断工作台（真正的产品）、规则库/知识库（维护诊断引擎的后台）、「从一个问题开始」（学习 / 新站规划 / 诊断三路分流的顾问会话）。
2. **系统围着「每次诊断（run）」转，用户关心的是「每个问题」**。决定不跨 run 继承，回测结果不回到问题上，所以环闭不上。
3. **同一批内容在 5 处各说一遍，结论还互相矛盾**。

另有一处逻辑错误：没执行过的建议在回测后被判「无效」，并流进规则进化统计。

## 一、功能盘点（按服务对象分组）

| 服务对象 | 功能 | 入口 | 状态 |
|---|---|---|---|

- 2 个项目，只有 metadocu.com 跑过诊断：5 次（4 次基线、1 次回测）。
- 建议 62 条：47 条待确认、15 条已接受、**0 条已执行**；生成的执行提示词 0 条；品牌事实 0 条。

## 二、三个结构问题

### 2.1 三个产品挤在一个导航里

- 主导航四项：项目 / 规则库 / 知识库 / 设置（`components/siteNav.ts:16-19`，observed）。
- 规则库副标题「自动发现、人工放行——第四道人工闸门」；知识库副标题「把外部变化变成可审计、可发布、可回滚的诊断能力」（浏览器，observed）。
- **规则库「发布」不改变诊断行为**：发版后需开发者手动同步代码常量 `RULES_VERSION`（`app/api/rules/release/route.ts:27`，observed）。诊断代码（`lib/diagnosis/`、`generate-findings.ts`）不读 `rule_change_proposals`，也不读 `reference_artifacts`（grep 零命中，observed）。
- 分析会话工作流 S1–S9 的节点全部是 `ruleIds: []`（`lib/knowledge/workflow.ts:26-35`，observed），对诊断的实际作用只有调整规则执行顺序（reported）。
- 会话页 `/sessions/[id]` 只有新建时那一次跳转能进入：没有列表，面包屑不可点，也不回链到 run（reported）。

### 2.2 以 run 为中心，问题没有跨次身份

- 同一项目诊断 5 次，库里 63 条发现，去重后只有 19 个问题，其中 6 个在 5 次里都出现了（按 `findings.fingerprint` 统计，observed）。
- `fingerprint` 只用于回测四态对齐；接受 / 否决 / 已执行 / 误报这些决定都不跨 run 继承（grep，observed）。每次新诊断都会生成一整套待确认建议。
- 项目页的诊断历史有 5 行，4 行显示「待复核 · 确认建议」（浏览器，observed）。
- 回测那次的概览没有前后对比，只要求「确认建议（12 条待确认）」（浏览器，observed）。
- 前后对比只出现在**基线**那次报告里一个默认折叠的章节（`ReportView.tsx:175` 按 `baselineRunId` 查询，reported）。回测那次自己的报告写着「尚无回测」（reported）。`/api/runs/[id]/delta` 没有任何界面调用（reported）。
- 每条建议的「有效 / 无效」判定，任何页面都不显示（reported）。
- 复查到期日 `nextRetestDueAt` 写进去后从不清空（全库没有置空的写入方，observed），也没有自动复查。

### 2.3 同一批内容多处重复，结论互相矛盾

- 最近一次诊断：12 个问题对应 11 条建议，一一对应，只有 1 条是「仅记录」（查库，observed）。同一批内容出现在概览前 3 条、问题、建议、执行清单、报告 5 处。
- **结论矛盾**：概览写「AI 目前不会主动推荐 metadocu：23 个不提品牌名的提问里，提到你 0 次」；同一次诊断的报告第一句是「网站整体状况良好，没有系统性大问题」（浏览器，observed）。原因是报告结论只看有没有严重技术问题和关键词数据，没把 AI 可见度算进去（`lib/diagnosis/report.ts:140-152`，observed）。
- **闸门口径矛盾**：报告「先做这 3 件事」取自优先级矩阵，矩阵包含全部建议（待确认、已否决都算），也不反映人工编辑的内容（`ReportView.tsx:367-372`、`report.ts:236-241`，`editedPayload` 无引用，observed）；同一份报告的「行动路线图」却写「尚无已采纳建议」。
- **报告有三份**：报告页（和分享页共用 `ReportView`）、Markdown 导出（另一套渲染）、执行清单页底部的「执行决策报告」。最后这份的 AI 摘要要配 OpenAI，和 10-04「先不引 LLM」的决定冲突（observed）。
- **分类口径有四套**：五支柱 P1–P5（发现、健康分）、11 个维度（`lib/runs/preflight.ts:4-6`）、工作流 S1–S9、报告的四种结论类型（observed）。

## 四、建议方向（derived，待拍板）

把主线收成一条，让「问题」成为项目级、跨诊断持续存在的对象：

```
项目 → 体检 → 问题清单（项目级，跨次追踪：新出现 / 仍在 / 已修复 / 未复查）
     → 方案报告（交付物，分享前整体审一次）→ 逐条标记已改 → 同协议复查 → 状态自动更新 → 下一轮
```

- 「问题」「建议」「执行清单」合成一张表，每行是：问题 + 怎么改 + 当前状态。
- 接受 / 否决（带理由）/ 已执行 / 误报，都挂在问题（fingerprint）上，跨次继承。
- 报告只留一份，结论按统一的优先级口径生成；分享版去掉内部溯源。
- 规则库、知识库、「从一个问题开始」移出主导航，放到「维护」区或下线。
- 至少有一条建议已执行，才能发起回测；判效果只算已执行的建议。回测结果写回问题状态，显示在项目页和问题清单上。

与在途工作的关系：子项目 B（检查台账 + 报告骨架，规格未写）和这里的报告、问题清单重设计重叠。建议先定本文的结构，再写 B 的规格，否则会在以 run 为中心的旧模型上继续叠加。

## 五、用户决定（2026-10-08）

1. 产品终点：**两个都要**——既交付优化方案报告，也跟踪执行 + 复查。即第四节的主线成立，报告是交付物，执行跟踪和复查是闭环。
2. 规则库、知识库、「从一个问题开始」：**先分清三块各是干什么的**，再决定去留。说明见第七节。
3. 断点 #1–#2：**要修**，已修复（未提交）：
   - 回测只给「回测开始前已执行」的建议判效果，其余写 `unknown`（`lib/diagnosis/retest-delta.ts` 的 `isRetestAttributable`，接线在 `lib/inngest/generate-findings.ts`）。
   - 规则效果统计只计执行过的建议，挡住库里残留的旧判定（`lib/diagnosis/rule-stats.ts`、`getRecStatRecords` 补读 `status/appliedAt`）。
   - 全量 234 个测试文件 / 2211 个测试通过；对真实库跑统计读取：12 条旧「无效」全部挂在待确认建议上，新过滤后执行过的是 0 条。
   - 库里这 12 条旧判定本身没有改，是否重置为 `unknown` 待用户决定。

## 六、风险与未核实

- 真实数据只有 metadocu 一个站，后半段（执行、复查、看效果）从未被真实走过，执行之后的体验没有观测数据。
- 标 reported 的条目来自代理读代码，主循环抽查过 #2、#4、#7 及「规则发布无运行时效果」「复查日期从不清空」「报告前 3 件事含全部建议」，其余未逐条复核。
- 断点 7 的后果推断（基线经竞品确认补进来的发现，回测时会被判「已修复」，建议进而被判「有效」）未实跑验证。
